How it works

Encryption, storage, and deletion are three separate steps.

1. Encrypt locally

Your browser generates a random 256-bit key with the Web Crypto API, derives a fresh 96-bit IV, and encrypts the message with AES-256-GCM. The authentication tag makes tampering detectable.

2. Store only ciphertext

The encrypted payload, the IV, and a SHA-256 hash of the key are sent to the server. The key itself stays in the URL fragment, which browsers do not include in HTTP requests.

3. Share one link

The recipient opens the link, confirms the retrieval, and decrypts the message in their own browser. The key hash lets the server reject the wrong key without ever seeing it.

4. Delete on read

The ciphertext is removed as soon as it is retrieved. Unread messages are deleted automatically after one hour, so abandoned links do not linger.

What the server can and cannot see

A precise picture is more useful than a marketing claim.

Stored on the server

  • Message ID, creation time, and the IV plus ciphertext
  • A SHA-256 hash of the encryption key, used only to verify retrieval
  • Creator IP address and browser user-agent (logs are deleted after 24 hours)
  • Recipient email address when OTP protection is enabled
  • Delivery metadata (time, IP, browser) once the message is read

Never stored on the server

  • Your plaintext message or attachment contents
  • The encryption key itself
  • The full message URL with its fragment
  • Any account, profile, or contact list — there are no accounts

AES-256 in GCM mode with a 128-bit authentication tag and a unique 96-bit random IV per message. All cryptography runs through the browser's native Web Crypto API. No hand-written cipher implementation and no legacy library are used.

The key is generated in your browser and placed after the # in the message URL. URL fragments are not sent to the server, so the key never appears in HTTP requests or server logs. The server receives only its SHA-256 hash so it can verify the right key is being used.
